Each run's raw reports are in `syn/runs/<run>/` (`info.txt` records the git commit). Placement noise is
about +/-0.5 ns at failing targets, so only differences larger than that mean anything.

Reading the table: against run 03 the change gains 0.43 to 0.67 ns at the three failing targets, but against the original run 01 the gain at 222 and 250 MHz is only about 0.3 ns, which is inside the +/-0.5 ns noise band. The WNS numbers alone do not prove the change helped. The evidence that it did is structural: the worst-path report at 222 and 250 MHz no longer contains the level-RAM -> carry chain -> occupancy-mask path that limited run 03.

What limits it next, in the order they appear at 250 MHz: (1) `mdp_lat_stats` chains a 40-bit subtract into a 40-bit compare (instrumentation only: register the difference before comparing, no effect on tick-to-trade); (2) the book's 32-bit level add feeding the level RAM write data, and the 32-bit remaining-quantity subtract whose carry-out drives 65 loads; (3) the framer's byte-count control cone.

Noise reference (same two-clock design, core clock 4.0 ns, only the network target changed): worst core-clock slack -0.145, -0.215, -0.335, -0.362, -0.691 ns. Treat differences under about 0.5 ns as noise.

How to add a run: `set RUN NN-short-name` and set `ASYNC_CORE` explicitly (0 for one clock, 1 for two), `source build.tcl`, then `syn\run_sweep_par.bat NN-short-name`.
